# Roles

A role is a named permission set stored in `team_roles` (id, name, colour, position, `system_key`, `flags`, `permissions`). **System roles are identified by `system_key`, never by name**, so renaming one can never grant or revoke rights: `owner` (single holder, always has every permission), `member` (the baseline every member carries), `default` (what non-members may do inside the team's claims) and `mayor` (scoped to a capitol block's chunks, masked to `MAYOR_ALLOWED_MASK`). Custom roles have `system_key IS NULL` and can be created, edited, reordered and deleted.

Membership is split in two: `team_members.role_id` is a member's **base role** (owner or member), and `member_roles` stacks any number of **extra roles** on top. Effective permissions are `owner ? all : OR(base, extras) | individual overrides`, computed once by `CapitolDatabase.getEffectivePermissions` and cached per team. Roles are ordered by `position`; higher means more power, and the owner sits at the top.

Every rule lives in `RoleManager`, backed by the pure, Minecraft-free `RoleRules`: hierarchy (strictly below), grant-what-you-hold, reserved names, system invariants (owner untouchable, system roles undeletable, one owner) and ops bypass (ops skip permission/hierarchy checks but never the system invariants). Commands and packet handlers both call `RoleManager`, so the rules can't drift apart, and the role and member screens only grey out what the rules would reject — the server re-checks everything.
